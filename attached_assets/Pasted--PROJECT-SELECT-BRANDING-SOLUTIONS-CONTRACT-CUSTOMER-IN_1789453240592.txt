## PROJECT: SELECT BRANDING SOLUTIONS — CONTRACT CUSTOMER INTEGRATION HUB

We want to extend the existing Select Branding Solutions production/contract customer platform so that our contract customers can integrate their own systems directly with ours.

This must be designed as a GENERIC, REUSABLE INTEGRATION FRAMEWORK.

Do NOT build an integration specifically for Abode Home & Gifts or Not On The High Street.

Abode will be our first real-world use case, but the architecture must allow future contract customers to connect their own:

* Websites
* Ecommerce platforms
* Bespoke order systems
* ERP systems
* Order management systems
* Shipping platforms
* Courier/carrier accounts

The long-term objective is:

CUSTOMER ORDER SYSTEM
↓
SELECT INTEGRATION API
↓
SELECT PRODUCTION PLANNER
↓
PRODUCTION
↓
PACKING / DISPATCH
↓
CUSTOMER'S CHOSEN SHIPPING SYSTEM
↓
TRACKING / DISPATCH DATA
↓
CUSTOMER ORDER SYSTEM

The customer should ultimately be able to send an order into Select, have us manufacture/personalise it, and receive dispatch/tracking information back without either business manually rekeying information.

---

# 1. FIRST PRINCIPLE — DO NOT BREAK EXISTING PRODUCTION

This is an extension of the existing Select production system.

Before making changes:

1. Audit the existing architecture.
2. Identify the existing order, job, customer, production planner and dispatch data models.
3. Identify existing APIs, webhooks and integrations.
4. Identify how contract customer orders currently enter production.
5. Identify how jobs move through production statuses.
6. Identify how dispatch/tracking is currently recorded.

Reuse existing architecture wherever sensible.

Do NOT create duplicate order systems or duplicate production records simply to support API orders.

All API-created jobs must ultimately become normal production jobs within the existing production workflow.

Do not disrupt any existing customer ordering, production planning or dispatch functionality.

---

# 2. CREATE AN INTEGRATION LAYER

Create a dedicated:

**Select Contract Integration Hub**

This should sit between external customer systems and our internal production system.

It must handle:

* Authentication
* Customer identification
* Incoming orders
* Validation
* Data transformation
* Product/SKU mapping
* Personalisation data
* Order status
* Production status
* Shipping instructions
* Dispatch
* Tracking
* Webhooks
* Error handling
* Retry handling
* Logging
* Audit history

External systems should NEVER communicate directly with internal production database tables.

Everything must pass through the integration layer.

# 4. INCOMING ORDER API

Create a secure REST/JSON API allowing approved contract customers to push orders into Select.

Suggested endpoint structure:

POST /api/v1/orders

GET /api/v1/orders/{order_id}

GET /api/v1/orders/{order_id}/status

POST /api/v1/orders/{order_id}/cancel

Actual routes should follow the existing application's architecture and conventions.

Do not blindly create these routes if equivalent functionality already exists.

# 6. MULTI-LINE ORDERS

The API MUST support:

One order → one product

One order → multiple identical personalised products

One order → multiple different products

One order → multiple different personalisations

Example:

ORDER 12345

1 × Red Stocking — SOPHIE
1 × Red Stocking — JACK
1 × Green Stocking — OLIVER

All three belong to the same customer shipment.

Production may treat these as separate production items, but fulfilment must understand that they belong to ONE external customer order.

This is extremely important.

---

# 7. IDEMPOTENCY / DUPLICATE PROTECTION

External systems will occasionally retry API calls.

We must NEVER accidentally create duplicate production orders.

Use:

Customer ID + external order reference

and/or an idempotency key.

If an identical order is submitted twice, the API should recognise it rather than creating another production job.

Log duplicate attempts.
